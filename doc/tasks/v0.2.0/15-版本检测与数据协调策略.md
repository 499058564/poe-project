## 任务描述

设计并实现统一的多数据源版本检测与数据协调策略。各数据源提供的数据版本粒度不同，需要在同步和查询时正确协调。

## 背景

| 数据源 | 版本粒度 | 示例 | 权威性 |
|--------|----------|------|--------|
| GGG API | 赛季名 + 版本号 | `3.25.0`, `Settlers` | 🔒 赛季权威 |
| Wiki Cargo | 每物品 release_version + 页面实时更新 | `Mageblood: 3.16.0`；最新物品在页面中 | ✅ 当前数据 |
| POB | 游戏构建版本 | `3.25.2b`（从 tree 数据提取） | 📦 客户端提取 |
| poe.ninja | 赛季名 | `Settlers` | 💰 经济时效 |

### 5. 同步策略决策树

```
开始同步
  │
  ├─ GGG API 可用？
  │   ├─ 是 → 获取当前赛季名（赛季权威）
  │   └─ 否 → 用 Wiki items max(release_version) + poe.ninja 赛季名
  │
  ├─ 表有 Wiki 覆盖？
  │   ├─ 是 → 从 Wiki Cargo API 同步（主数据源，全部可用）
  │   └─ 否 → 尝试替代源
  │
  ├─ 表需要 POB 数据？
  │   └─ 仅作完整性验证；Wiki 足以覆盖所有核心数据
  │
  ├─ 表是经济数据？
  │   ├─ 是 → poe.ninja 同步
  │   └─ 否 → 跳过
  │
  └─ 记录 data_version（含 source + source_version）
```

## 验收标准

- [ ] `VersionDetector.getCurrentVersion()` 返回正确的当前赛季/版本号
- [ ] `isWikiDataStale()` 正确检测 Wiki 数据过期
- [ ] `data_version` 表支持多源版本记录
- [ ] `DataSourceHealthCheck` 启动时报告所有源可用性
- [ ] 多源协调同步不覆盖更新版本的数据
- [ ] 各数据源的同步结果合并后无数据冲突
- [ ] 单元测试覆盖版本检测和协调逻辑
